# Безопасность

Отчёт об аудите безопасности (октябрь 2026) и описание защитных механизмов.

## Как проводился аудит

1. **Ревью кода** по категориям: аутентификация и сессии, CSRF, права доступа, валидация ввода,
   XSS, работа с S3 (presigned URL, CORS), заголовки, хранение секретов, утечки информации,
   отказ в обслуживании, зависимости (`npm audit` — 0 уязвимостей).
2. **Атаки на запущенную систему** (эмулятор S3 moto и SeaweedFS — последний, в отличие от moto,
   проверяет подписи SigV4): подделка и повтор токенов, CSRF, повышение прав, выход за пределы
   папки, обход путей в статике, подмена IP, загрузка сверх лимита, XSS через имена в браузере,
   внедрение в журнал, недоступные хранилища.
3. Каждая найденная проблема воспроизведена до исправления и проверена после; на исправления
   добавлены регрессионные тесты (`test/app.test.js`, раздел «аудит»).

## Найдено и исправлено

| # | Уровень | Проблема | Исправление |
|---|---|---|---|
| 1 | Средний | **Обход лимита размера.** Presigned PUT не ограничивал объём: по ссылке, выданной на 1 байт, загружалось 3 МБ; не вызвав `/uploads/complete`, можно было обойти лимит размера и квоты. | Размер входит в подпись ссылки (`Content-Length`): S3 отклоняет загрузку другого объёма (проверено на SeaweedFS: 3 МБ → 403, 1 байт → 200). |
| 2 | Средний | **Сессия не отзывалась при выходе.** Токен оставался действительным до истечения срока — украденная cookie работала после «Выйти». | Выход отзывает токен (список отозванных — в памяти и `data/revoked.json`, 0600). В токен добавлена случайная часть, чтобы повторный вход в ту же секунду не совпал с отозванным. |
| 3 | Средний | **Зависание из-за «молчащего» хранилища.** У S3-клиента не было таймаутов: недоступное хранилище подвешивало список файлов для всех и запрос администратора (4+ минуты). | Таймауты соединения 5 с и ожидания 60 с; недавно упавшее хранилище при чтении пропускается сразу и перепроверяется раз в 30 с (список — 8 мс вместо 10 с). |
| 4 | Средний* | **Подмена IP через `X-Forwarded-For`.** При прямом доступе к Node (минуя Nginx) клиент подставлял любой IP и обходил ограничение попыток входа. | `X-Forwarded-For` учитывается только у соединений с локального/частного адреса (Nginx). С внешнего адреса — реальный IP, лимит срабатывает. |
| 5 | Низкий | **Подмена расширения невидимыми символами.** Имя `invoice‮fdp.exe` отображалось как «invoiceexe.pdf»; принимались невидимые пробелы в именах папок. | Bidi-символы и невидимые символы вырезаются из имён файлов и папок (ZWJ в эмодзи сохраняется). |
| 6 | Низкий | **Исполнение SVG на домене хранилища.** Ссылка предпросмотра отдавала SVG как `inline` — при прямом открытии скрипт из загруженного файла выполнялся на домене S3. | Предпросмотр — с `Content-Disposition: attachment` для всего, кроме PDF: `<img>`/`<video>` отображают файл, а прямое открытие ссылки его скачивает. |
| 7 | Низкий | **Утечка внутренней инфраструктуры.** Обычные пользователи видели в предупреждениях адреса и порты хранилищ (`connect ECONNREFUSED 10.x.x.x:9000`). | Подробности ошибок хранилищ видит только администратор; остальным — «нет связи с хранилищем». |
| 8 | Низкий | **Служебные ключи в настройках.** `constructor`, `toString` принимались как названия настроек и сохранялись в `settings.json`. | Только собственные ключи описания (`Object.hasOwn`); неизвестные настройки — ошибка 400. |
| 9 | Низкий | **Нет журнала безопасности.** Неудачные входы и удаления нигде не фиксировались. | `[auth]` — входы и неудачные попытки (для fail2ban), `[audit]` — загрузка, удаление, перемещение, папки, пользователи, настройки. Значения пишутся через JSON — перевод строки в логине не подделает запись. |
| 10 | Инфо | Не было `Permissions-Policy`; у статики, отдаваемой Nginx, не было `nosniff`. | Заголовки добавлены (приложение и `deploy/nginx.conf.example`). |

\* Средний — если Node доступен извне в обход Nginx (например, `HOST=0.0.0.0`); при рекомендуемой
настройке (`HOST=127.0.0.1`) атака была невозможна.

## Проверено — защита работает

- **Аутентификация:** пароли — scrypt (N=16384, r=8), сравнение за постоянное время; время ответа
  при существующем и несуществующем логине одинаковое (68/66 мс) — перебор логинов невозможен;
  одинаковое сообщение об ошибке. 10 попыток входа за 15 минут с IP.
- **Сессии:** HMAC-SHA256, срок жизни, подпись привязана к хешу пароля (смена пароля / удаление
  пользователя завершает сессии). Cookie: `HttpOnly`, `SameSite=Strict`, по HTTPS — `Secure` и
  префикс `__Host-`. Поддельная подпись, подмена логина, истёкший токен — отклоняются.
- **CSRF:** изменяющие запросы — только с `APP_ORIGIN` (Origin / Sec-Fetch-Site), плюс SameSite=Strict.
- **Права:** роли проверяются на сервере для каждого маршрута; редактор не может повысить себя,
  перезапустить сервер или открыть настройки; последнего администратора нельзя понизить или удалить.
- **Ввод:** ключи файлов и пути папок — строгий шаблон (выйти за папку хранилища нельзя), ссылки
  «хранилище:ключ», курсоры, uploadId, номера частей, TTL ссылок, MIME-типы; JSON до 32 КБ.
- **Статика:** `../`, `%2e%2e`, `%00`, скрытые файлы (`.env`, `data/`) — 404.
- **XSS:** все пользовательские данные выводятся через `textContent`; строгая CSP без inline-скриптов
  и стилей. Проверено в браузере: имена файла, папки и хранилища с `<img onerror>` показаны текстом.
- **Предпросмотр:** тип ответа задаёт сервер по белому списку; HTML/JS отдаются как `text/plain`.
- **Секреты:** ключи S3 и секрет сессий не передаются в браузер; `data/` — 0700, файлы — 0600.
- **Зависимости:** единственная runtime-зависимость — AWS SDK v3; `npm audit` — 0 уязвимостей.

## Загрузка по ссылке (защита от SSRF)

Сервер сам скачивает файл по ссылке пользователя — значит, мог бы стать «прокси» во
внутреннюю сеть (метаданные облака `169.254.169.254`, панель на `127.0.0.1`, соседние
серверы). Поэтому (`src/url-import.js`):

- только `http`/`https`, без логина и пароля в адресе;
- имя хоста разрешается заранее; если **хоть один** IP частный, локальный, служебный или
  зарезервированный (включая IPv4 внутри IPv6 `::ffff:…`) — отказ;
- соединение идёт на **тот же проверенный IP** (подмена `lookup`) — DNS rebinding не сработает;
- каждый редирект (до 5) проверяется заново — проверено: публичная ссылка с редиректом на
  `127.0.0.1` и `169.254.169.254` отклоняется;
- лимит размера (`MAX_FILE_SIZE_MB`) — и по `Content-Length`, и по факту при скачивании;
  таймаут 30 с; не больше 2 загрузок на сервер и 1 на пользователя;
- файл не хранится целиком: части по 5 МБ уходят в S3 по мере скачивания;
- доступно ролям «Редактор» и «Администратор»; в журнал пишется только хост, без пути и
  параметров ссылки (в них бывают токены).

## Остаточные риски (приняты осознанно)

| Риск | Почему принят | Что можно сделать |
|---|---|---|
| Администратор может указать любой адрес хранилища (сервер к нему обратится — SSRF) | Администратор — доверенная роль | Не выдавать роль «Администратор» лишним людям |
| Ссылки на скачивание (до 7 дней) нельзя отозвать | Особенность presigned URL S3 | Сократить срок по умолчанию; для отзыва — переместить или удалить файл |
| Ограничение попыток входа — по IP, не по учётной записи | Блокировка по логину позволила бы злоумышленнику заблокировать администратора | fail2ban и `limit_req` в Nginx (ниже) |
| scrypt N=16384 ниже рекомендации OWASP (N=2¹⁷) | N=2¹⁷ требует 128 МБ на вход — недопустимо на VDS с малой ОЗУ | Длинные пароли (≥ 10 символов обязательны) |
| Части multipart-загрузки по отдельности не ограничены по размеру | Итоговый размер проверяется при завершении, брошенные загрузки удаляет lifecycle-правило | Включить `deploy/s3-lifecycle.json` |
| Ключи S3 хранятся в `data/settings.json` открытым текстом | Шифрование потребовало бы хранить ключ рядом | Права 0600, ключи с доступом только к нужному бакету |
| Приложение не проверяет, что бакет приватный | Нет единого API у провайдеров | Создавать бакеты приватными (инструкция, шаг 3) |

## Рекомендации по эксплуатации

1. `HOST=127.0.0.1` (по умолчанию) — Node доступен только через Nginx; порт 3000 закрыт файрволом.
2. HTTPS обязателен (Let's Encrypt в FastPanel); `APP_ORIGIN` — с `https://`.
3. fail2ban: `deploy/fail2ban/file-manager.conf` → `/etc/fail2ban/filter.d/`,
   `deploy/fail2ban/file-manager.local` → `/etc/fail2ban/jail.d/`, затем `systemctl restart fail2ban`.
4. Nginx `limit_req` для `/api/auth/login` — см. `deploy/nginx.conf.example`.
5. Ключи S3 — с правами только на свой бакет; бакеты приватные; lifecycle-правило для брошенных загрузок.
6. Резервные копии `data/` (пользователи, настройки); при компрометации — «Завершить все сессии»
   в настройках и смена паролей.
